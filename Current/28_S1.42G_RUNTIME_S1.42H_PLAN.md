### BCMER root cause in final run

Immediately before level generation, BCMER 1.71.0 logged:

`Inside Spawn Curve`
- Time 0 -> -100
- Time 1 -> -100

`Outside Spawn Curve`
- Time 0 -> -100

Therefore the final run's no-enemy result is directly explained by BCMER-owned day state, not by EnemyScan.

For the focused EnemyIsolation validation, BCMER is a confounder and must be disabled temporarily.

## EnemyIsolation lifecycle bug

The final run contains **zero** EnemyIsolation apply markers.

S1.42G keyed the diagnostic application to a changed `SelectableLevel` object reference. Repeated runs on the same moon reuse the same level object, so a new day/run does not trigger reapplication.

Technical evidence from the earlier combined-log segments additionally shows that applying at route time is too early: later mods can repopulate the enemy pools before the spawn predictor runs.

Conclusion:
**EnemyIsolation must bind to every generated round at late generation/spawn lifecycle points, not to route/currentLevel reference changes.**

## BCMER DoorFailure / "Door System: ERROR"

Earlier technical evidence in the combined log shows BCMER calling:
`BrutalCompanyMinus.Minus.Handlers.HangarShipDoorPatches.OverwriteDoorPower`

BCMER upstream behavior while DoorFailure is active:
- sets `doorPower = 0`;
- calls `SetDoorOpen()` every Update;
- disables door buttons;
- alternates FAILURE/RETRYING display text.

The enormous screenshot/log output was amplified by this project's old DoorAudit prefixes, which captured a fresh stack trace on every `SetDoorOpen` / `SetDoorClosed` / `PlayDoorAnimation` call.

S1.42H:
- removes those per-call stacktrace audits;
- keeps the useful door state-change audit;
- keeps the anti-lockout failsafe;
- detects the forced-open zero-power state only on transition;
- leaves BCMER's intended DoorFailure event behavior intact.

This compatibility fix is carried forward even though BCMER is disabled in the S1.42H focused EnemyIsolation profile.
