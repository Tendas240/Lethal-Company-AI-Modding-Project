## Question

Phase C2 asks why the 14 current `AUTHOR_OR_OWNER_HARD_BLOCK` cells are blocked before any override or targeted runtime test is designed.

The evidence standard is deliberately conservative:

- classify a block as an **explicit compatibility safeguard** only when repository evidence ties the moon exclusion itself to a technical compatibility reason;
- classify it as **author default targeting/balance** when the package's own matching defaults explain the exclusion by positive target lists, tag families, route-price rules, or explicit zero rarity without a technical reason;
- classify it as an **unexplained owner exclusion** when an explicit block exists but the repository does not establish why the author requires it;
- keep separate technical defects separate unless repository evidence proves that they caused the exact moon exclusion.

The pattern is internally consistent rather than a generic package failure:

- DULL's Abandoned Foundry, Gray Apartments, Spelunkers Random, Spelunkers Magmatic and Sub Systems are viable on Offense while other DULL flows are rejected according to different owner target metadata.

Therefore the 12 Offense exclusions are not evidence that their package owners fail registration or generation globally.

## Shatteredrooms × Experimentation and × Embrion

The generated owner default is explicit:

`Experimentation:0,...,Offense:75,...,Embrion:0,...`

Historical repository research further records:

- Shatteredrooms has a known CullFactory incompatibility;
- author guidance says it cannot appear on Experimentation/Embrion and the project must preserve that restriction.

What the repository **does not** establish is the technical reason why those two moons are forbidden.

Accordingly both cells are classified:

**UNEXPLAINED_EXPLICIT_OWNER_EXCLUSION**

They are not downgraded to ordinary balancing merely because the numeric value is zero, because the repository separately preserves an author "cannot appear" instruction. They are also not promoted to `KNOWN_TECHNICAL_RESTRICTION`, because no entrance-count, teleport, DunGen, geometry, CullFactory, elevator, routing or NavMesh mechanism has been causally tied to those two exact moon pairings.

The known CullFactory incompatibility remains a separate technical risk affecting the interior generally. It does not prove why Experimentation and Embrion alone are blocked.

## Important negative finding

Phase C2 found **no hard-block cell for which the repository currently proves an explicit technical moon-pair safeguard**.

This does not prove all 14 restrictions are safe to remove.

It means the current evidence distinguishes:

1. owner/theme/balance targeting that is not itself technical-safety evidence;
2. explicit Shatteredrooms author exclusions whose technical reason remains unknown;
3. separate known compatibility defects that still require resolution before universal technical safety can be claimed.
