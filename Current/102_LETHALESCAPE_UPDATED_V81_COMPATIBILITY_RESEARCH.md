# LethalEscapeUpdated V81 Compatibility Research

**Date:** 2026-09-04  
**Status:** RESEARCH PRESERVED / DEFERRED UNTIL S1.42AB GATE CLOSES / DO NOT ADD TO AB

## User goal

The user remembers an older juijui-profile gameplay aspect where some indoor enemies could leave the facility and appear/fight outside. The desired future behavior is **cross-boundary enemy escape/follow behavior**, not arbitrary extra enemy spawning that changes the accepted spawn/power baseline.

## Historical identification

The remembered mechanic matches the design of **LethalEscape** very closely:

- original package: `xCeezy-LethalEscape-0.8.5`;
- Thunderstore marks the original package deprecated;
- package description: allows almost every inside creature to escape outside;
- old changelogs include extensive inside -> outside AI transition work.

However, the repository does **not** currently prove that the old juijui profile specifically contained LethalEscape. `Archive/S1.31/CurrentMetadata/Aktive_Modliste_S1.31.txt` does not list it. Therefore do not state as a fact that juijui used LethalEscape unless a direct older juijui export/source proves it later.

## Current V81 successor

Current strong candidate:

`woah25-LethalEscapeUpdated-2.5.0`

Thunderstore's current changelog explicitly states for 2.5.0:

`updated to v81 and a ton of bug fixes`

Current Thunderstore classification includes server-side / monsters / tweaks & quality-of-life. The package page also states that it no longer requires everyone to have the mod because of AI ownership override behavior.

This makes `woah25-LethalEscapeUpdated 2.5.0` the obvious V81-era successor to evaluate for the remembered mechanic.

## Relevant historical feature evolution

The maintained/fork changelog shows that the project has historically handled many of the exact transition problems relevant to this modpack:

- enemies walking to exits before teleporting outside;
- emergency-exit fallback when main entrance is unreachable;
- Flowerman/Bracken return-inside behavior;
- first outside enemy entering the facility;
- Baboon Hawk support;
- AI-node fixes;
- Baboon pathing-to-entrance fixes;
- major rewrite at 2.0.0;
- V81 update + bug fixes at 2.5.0.

Historical support is useful context but is **not** proof that every old config key or per-enemy option still exists in 2.5.0 after the major rewrite.

## Important source-code caveat

The Thunderstore package points to:

`https://github.com/xCeezyx/LethalEscape`

but the visible `main` source previously inspected appeared stale around the old 0.8.x implementation rather than representing the exact current 2.5.0 package.

Therefore:

- do not infer current 2.5.0 config keys from the old GitHub source;
- do not assume old per-enemy options survived the major rewrite unchanged;
- before building a candidate, inspect the **actual Thunderstore 2.5.0 package** and/or a config generated by 2.5.0;
- freeze exact package version and exact discovered config semantics in the build plan.

## Current project compatibility risk

The current project stack already contains substantial AI/pathfinding behavior, including the known project combination of:

- SmartEnemyPathfinding;
- PathfindingLib;
- PathfindingLagFix;
- FairAI;
- LethalMin / Pikmin AI and its project-local compatibility fixes;
- many custom moons and interiors with varying NavMesh quality.

No documented direct incompatibility was found during the initial research between current LethalEscapeUpdated and SmartEnemyPathfinding, FairAI or LethalMin. Historical/community modpacks have also used LethalEscape and FairAI together.

That is only suggestive evidence. It is **not** sufficient proof for this project's large V81 stack. An isolated runtime candidate is mandatory.

## Performance / NavMesh warning

A separate small package currently exists:

`pierre67-LethalEscapeThrottle-1.0.1`

Its author describes a performance failure mode in LethalEscapeUpdated on difficult NavMeshes: enemies that cannot reach an exit may repeatedly call `AIBridge.RequestTransition`, causing repeated NavMesh path calculations and heavy log spam. The throttle adds a per-enemy cooldown after failed escape attempts.

This is useful diagnostic evidence because this project already has many custom moons/interiors and has just observed a Black Mesa/Pikmin unreachable-route case.

Do **not** automatically add LethalEscapeThrottle:

- it is a very small/new third-party addon;
- it had extremely little adoption at research time;
- its necessity must first be demonstrated in this exact stack.

Instead, explicitly monitor for the described retry/path/log-spam pattern during any future LethalEscapeUpdated candidate. Only evaluate a throttle/fix if the problem reproduces.

## Recommended future candidate design

Do **not** add LethalEscapeUpdated while S1.42AB's interior-weight runtime gate is still open.

After AB is accepted/rejected and the project returns to a stable baseline:

1. inspect the actual `woah25-LethalEscapeUpdated 2.5.0` package and generated config;
2. freeze exact package/config behavior in a dedicated plan;
3. build a dedicated isolated candidate from the then-current accepted baseline;
4. add no unrelated balancing/config changes to the same candidate;
5. preserve the accepted normal enemy spawn/power baseline;
6. disable arbitrary/direct outside-spawn options initially wherever 2.5.0 actually exposes such controls;
7. target escape/follow transitions rather than new outside-spawn population;
8. be especially conservative around Baboon Hawks because the project's LethalMin/Pikmin Baboon lifecycle has a known fragile history;
9. if 2.5.0 exposes a Baboon Hawk transition toggle, disable it in the first candidate;
10. prefer first-pass coverage around established indoor enemies such as Thumper, Bracken/Flowerman, Hoarding Bug, Spider, Puffer/Spore Lizard and possibly Nutcracker before expanding to riskier cases.

Jester/Coil Head or other special-state enemies may need separate judgment because their AI/state assumptions can differ materially from normal pursuit enemies.

## Required runtime gate for a future LethalEscapeUpdated candidate

At minimum verify:

- plugin loads with exact intended version;
- indoor enemy can transition through an entrance to outside;
- transition uses sensible main/emergency-exit fallback behavior;
- enemy remains functional after transition;
- enemy can still target/attack appropriately outside;
- no duplicate enemy objects;
- no repeated inside/outside teleport loop;
- no stuck entrance state;
- no `AIBridge.RequestTransition`/NavMesh retry flood;
- no material FPS/frame-time regression;
- no massive log spam;
- no custom-moon/interior transition exception flood;
- SmartEnemyPathfinding remains healthy;
- FairAI remains healthy;
- LethalMin/Pikmin lifecycle remains healthy;
- Baboon Hawk/Pikmin narrow compatibility architecture remains intact;
- accepted normal enemy spawn/power baseline remains intact;
- Fatal = 0;
- no new project-local/transition exception class.

## Do-not-regress constraints

Never use LethalEscapeUpdated as justification to:

- disable `LethalMin.BaboonBirdPikminEnemy` globally;
- alter the accepted Hawk -> Pikmin narrow block without dedicated evidence;
- block Pikmin -> Baboon Hawk attacks;
- disturb inherited PikminEnemy lifecycle cleanup;
- change accepted normal enemy spawn/power values merely to make testing easier without restoring them exactly afterward;
- silently introduce direct outside-spawn probability when the intended feature is facility escape;
- combine the test with unrelated deferred balance work.
