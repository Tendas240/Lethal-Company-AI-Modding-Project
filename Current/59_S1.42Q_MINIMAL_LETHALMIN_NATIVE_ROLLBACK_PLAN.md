# 59 — S1.42Q Minimal LethalMin-Native Rollback Plan

**Date:** 2026-09-03  
**Status:** canonical next-stage design direction; no S1.42Q build created yet.

## Design goal

Return Pikmin gameplay as far as possible to **native LethalMin behavior**.

The project-local compatibility plugin must not reimplement LethalMin's normal:

- Pikmin -> enemy targeting;
- Pikmin -> enemy latch/attack;
- enemy-death task completion;
- Pikmin -> enemy-body carrying;
- corpse delivery to Onion.

Those systems should be owned by LethalMin.

The only intended deviation is the user's explicit protection rule:

> **Enemies must not target, attack, grab, bite, poison, or otherwise harm Pikmin.**

Where LethalMin already provides a reliable config switch for that direction, prefer the config switch.

Project-local code should exist only for proven gaps where the upstream/config path does not prevent the unwanted Enemy -> Pikmin interaction.

## Why this supersedes the previous S1.42Q idea

S1.42P confirmed:

- exact `PikminAI.FinishTask()` works;
- adding a custom Hawk-death finalizer nevertheless creates unnecessary ownership of LethalMin task lifecycle;
- fixed-distance attacker selection is incomplete;
- finalized Pikmin can immediately re-enter LethalMin's normal enemy-discovery logic.

Rather than adding another custom layer for target identity and dead-Hawk filtering, the cleaner solution is:

**stop intercepting the Pikmin -> enemy lifecycle at all.**

Let the stock LethalMin attack task observe the stock enemy death lifecycle.

## Native behavior evidence

LethalMin's documented intended behavior includes:

- thrown Pikmin latch onto and attack enemies;
- enemy bodies are carried to the Onion.

The S1.42P runtime also proved the body-carry path is healthy:
13 Yellow Pikmin carried `BaboonHawkBody(Clone)` and the body reached the Onion.

Therefore project-local task/carry replacement logic is not required.

Comparing:

- `ProfileSources/S1.42P/BepInEx/config/NoteBoxz.LethalMin.cfg`

shows only **one** LethalMin config difference:

`[Enemy Behavior] Thumper Bite Limit`

- S1.41 accepted baseline: `3`
- S1.42P diagnostic descendant: `0`

All core native LethalMin behavior was already present in S1.41, including:

- `Invinceable Pikmin = true`
- `No Knock Back = true`
- `Pikmin Die In Player Death Zones = false`
- `Convert Enemy Bodies To Items = true`
- native Attack Blacklist
- CodeRebirth compatibility switches
- enemy-specific protection switches such as `Puffer Can Poison Pikmin = false`, `Old Bird Grabs Pikmin = false`, etc.

S1.42Q should restore `Thumper Bite Limit = 3` unless runtime evidence proves a separate reason not to.

## Code to remove from the Pikmin -> enemy path

### 1. Remove BaboonHawkDeathCleanup completely

Remove:

- `PatchBaboonHawkDeathCleanup()`
- `BaboonHawkDeathCleanup`
- exact `BaboonBirdAI.KillEnemy(bool)` postfix
- `PikminAI.FinishTask()` reflection/resolver
- `DeathReleaseRadius`
- `RoundManager.SpawnedEnemies` Hawk-death Pikmin enumeration
- all manual Hawk-death task finalization.

Reason:

This owns a lifecycle that should remain native LethalMin.

### 2. Remove post-grab state repair / reflective restoration

The current `LethalMinGrabBiteStateRepair` does more than prevent unwanted interaction:

- snapshots leader/follow/grab state;
- searches for release methods;
- waits after a grab;
- restores reflected fields/properties if the survivor is leader-less.

This is recovery code for an interaction that should never be allowed to begin.

S1.42Q should move to **prevention before mutation** and remove the post-grab repair machinery where possible.

Target simplification:

- no delayed repair coroutine;
- no leader/follow member snapshot;
- no reflective field/property restoration;
- no release-method guessing.

### 3. Do not patch native AttackEnemy / CarryItem behavior

Do not add:

- dead-Hawk AttackEnemy target filters inside Pikmin task code;
- custom Pikmin attack target registries;
- custom corpse carry state;
- custom Onion routing;
- custom FinishTask/RemoveCurrentTask calls for enemy death.

If stock LethalMin still fails after our custom task lifecycle is removed, capture a clean native reproduction first before adding a new compatibility shim.

## Enemy -> Pikmin side: keep only proven necessary protection

### Native config first

Prefer existing LethalMin config toggles wherever they already express the desired rule.

Examples currently configured:

- Puffer poison disabled;
- Old Bird grabbing disabled;
- Forest Keeper grabbing disabled;
- Circuit Bee zap/kill disabled;
- Hydrogere trap/kill disabled;
- Company grab/hear disabled;
- Maneater/Masked-related controls;
- CodeRebirth Pikmin-affecting toggles disabled.

Do not replace a working upstream config switch with Harmony code.

### Proven external gaps may retain narrow shims

Some behavior has already been runtime-proven to bypass config and can remain as a compatibility shim, provided it does not touch normal Pikmin attack/carry logic.

Examples:

- CodeRebirth Autonomous Crane utility-kill protection, because runtime previously proved the LethalMin crane toggles alone were insufficient;
- narrow Puffer effect protection only if the native `Puffer Can Poison Pikmin = false` path still fails in the current Nightly;
- narrow enemy Grab/Bite prevention for a proven LethalMin adapter gap.

### Preferred prevention shape

For enemy Grab/Bite defects, prefer:

**block the exact Enemy -> Pikmin entry point before it mutates Pikmin state.**

Avoid:

**allow the grab, then repair Pikmin afterward.**

A central exact `PikminAI.GrabPikmin(...)` prefix may remain only if it can reliably prove the call represents an unwanted Enemy -> Pikmin interaction and can simply return before mutation.

Do not retain its current reflection-heavy post-repair system merely as insurance.

## Baboon Hawk protection

Desired final behavior:

- Pikmin -> living Baboon Hawk: native LethalMin attack/latch/kill;
- living Baboon Hawk -> Pikmin: no target/chase/bite/grab;
- Hawk death: native LethalMin task lifecycle;
- Pikmin -> Dead Baboon Hawk body: native LethalMin/SellBodies carry to Onion.

The current Baboon adapter disable / BitePikmin / GrabPikmin protection should be reduced to the **smallest proven set that blocks only Hawk -> Pikmin**.

Do not disable or patch anything solely to influence Pikmin -> Hawk attack behavior.

## Dead Baboon Hawk corpse guard

`BaboonHawkCorpseProtection.CanGrabScrapPostfix` is **not** a Pikmin carry implementation.

It only prevents a living Baboon Hawk from treating the SellBodies Dead Baboon Hawk item as ordinary scrap.

S1.42P runtime proved:
- Pikmin can still carry the corpse;
- body reaches Onion;
- living Hawk ignores corpse.

Therefore this guard may remain as a narrow SellBodies/Baboon-Hawk compatibility shim unless a clean native test proves it is no longer necessary.

## Temporary diagnostics

EnemyIsolation remains enabled for the rollback validation.

Exact BCMER 1.71.0 remains disabled.

Do not restore the normal enemy baseline or BCMER until the minimal rollback passes.

## S1.42Q acceptance test

The purpose of S1.42Q is not to test another custom death algorithm.

It must test the **absence** of unnecessary custom Pikmin lifecycle code.

Required:

1. Pikmin can attack/latch onto living Thumper/Crawler using native LethalMin.
2. Pikmin can attack/latch onto living Baboon Hawk using native LethalMin.
3. When the enemy dies, attacking Pikmin leave the attack naturally without project-local FinishTask/RemoveCurrentTask.
4. All attacking Pikmin remain visible/responsive and can be whistled back.
5. Following count is unchanged after recovery.
6. Pikmin can carry the Dead Baboon Hawk using native body-carry behavior.
7. Corpse reaches Onion.
8. Enemy -> Pikmin attacks/grabs/bites remain blocked.
9. Puffer does not poison/effect Pikmin.
10. No `Work state with no task assigned!` loop.
11. No `Leader is null when following` loop.
12. No project-local `BaboonHawkDeathCleanup` runtime markers should exist.

## Philosophy / anti-regression rule

For Pikmin gameplay:

**upstream first, compatibility shim second.**

Every custom hook must answer:

1. Which explicit user requirement does it implement?
2. Which exact upstream/config behavior failed?
3. What runtime evidence proves the shim is still necessary?
4. Does the shim touch only the unwanted Enemy -> Pikmin direction?

If those questions cannot be answered, remove the hook rather than carrying it forward.
