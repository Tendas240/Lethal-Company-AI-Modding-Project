## Decision

The smallest useful diagnostic surface is a read-only correlation layer around the already-proven Dusk selection/replacement path, the exact Janitor blendshape-write callsites, and the Unity log pipeline. It must not alter enemy selection, Dusk RNG state, replacement actions, renderers, meshes, bones, materials, blendshape weights, AI/network state, dungeon selection, profile/config/package bytes, or runtime controllers.

The design is intentionally narrower than a profiler or general renderer tracer. Full renderer snapshots are required only for Janitor and SpringMan. Other enemies receive only lightweight identity/replacement-selection markers when relevant. The exact stackless `Array index (0) is out of bounds (size=0)` message is observed at the log pipeline boundary without assuming that Unity native blendshape code owns the emission.

This design closes the instrumentation-design checkpoint only. It does not authorize C# implementation, a source/static patch checkpoint, an inactive review build, publication, Gale import, activation, or a runtime run.

## Correlation identity and timestamp contract

Every diagnostic record must carry the same correlation envelope:

- event kind;
- UTC timestamp and local timestamp;
- monotonic `Stopwatch.GetTimestamp()` value;
- Unity frame number when emitted from the main thread;
- enemy component `GetInstanceID()`;
- enemy GameObject `GetInstanceID()`;
- enemy runtime type and `enemyType.enemyName`;
- `NetworkObjectId` when a spawned `NetworkObject` is available, otherwise explicit `null/unspawned`;
- `OwnerClientId` when available;
- current exact-array-signature count already observed by the diagnostic;
- tracked renderer `GetInstanceID()` where the event is renderer-specific.

The monotonic timestamp is the primary cross-record ordering key. Wall-clock timestamps exist to align diagnostic records with the existing `LogOutput.log` format.

## Required hook 1 — Dusk replacement decision state

### Exact source point

Exact DawnLib.Dusk 0.9.25 source evidence shows:

`EntityReplacementRegistrationPatch.ReplaceEnemyEntity(orig_Start orig, EnemyAI self)`

at the selection path preserved in `SourceEvidence/BMAFR1Performance/20261002T173617Z/SOURCE_EXCERPTS.json`, with the selected non-default definition applied by:

`StartCoroutine(current.Apply(self))`

after `orig.Invoke(self)`.

### Observation design

Two read-only observations are required:

1. a prefix on the exact resolved `DuskEnemyReplacementDefinition.Apply(EnemyAI)` call target records a selected non-default definition before its coroutine begins;
2. a postfix on exact `EntityReplacementRegistrationPatch.ReplaceEnemyEntity(..., EnemyAI self)` records the completed selection state for Janitor/SpringMan and any enemy for which a non-default Dusk definition was observed.

The selected-definition record must include:

- stable replacement key when exposed by the exact Dusk registration metadata;
- Unity object/asset name;
- concrete runtime definition type;
- `IsDefault`;
- replacement-definition instance ID;
- action manifest: concrete action type plus `HierarchyPath` for every action that exposes the exact Dusk `Hierarchy` contract.

If the exact Dusk 0.9.25 action collection/key member cannot be resolved by declared member identity during a later source/static implementation checkpoint, that implementation must fail closed. No fuzzy field-name scan is permitted.

The selector-postfix state must be explicit:

- `SELECTED_NONDEFAULT` when the Apply observation fired for that enemy instance;
- `ALREADY_REPLACED` when Dusk reports an existing replacement before a new selection;
- `NO_DUSK_DEFINITION` when the enemy has no replacement-definition collection;
- `NO_NONDEFAULT_REPLACEMENT` when no non-default Apply occurred. This covers Dusk default/no-replacement outcomes without consuming or replaying the shared RNG.

The diagnostic must never call `Random.Next`, rerun Dusk weight selection, reorder candidates, or infer selection from map seed.

## Required hook 2 — exact Dusk skinned-mesh transfer

### Exact source point

Exact DawnLib.Dusk 0.9.25 source:

`SkinnedMeshReplacement.ReplaceSkinnedMeshRenderer(SkinnedMeshRenderer targetSkinned)`

performs the concrete mutation after the iterator delay. The reviewed body reads original materials/root, builds the target-bone lookup, maps replacement bones by name with root fallback, assigns `targetSkinned.sharedMesh = ReplacementRenderer.sharedMesh`, assigns bones/rootBone, and then calls `MaterialsReplacement.CopyOrResizeMaterials(..., newMesh.subMeshCount)`.

### Harmony surface

Use a prefix and postfix on this exact private instance method only. Do not patch the iterator `Apply` state machine and do not patch a broad Renderer/Transform API.

The prefix captures:

- Dusk action type = concrete `SkinnedMeshReplacement` runtime type;
- exact `HierarchyPath`;
- target renderer name, relative hierarchy path, instance ID, enabled state;
- original mesh name/instance ID;
- original `blendShapeCount` and every blendshape name;
- original material count;
- original mesh `subMeshCount`;
- original rootBone name/path/instance ID;
- original target bone names;
- replacement renderer name/instance ID;
- replacement mesh name/instance ID;
- replacement `blendShapeCount` and every blendshape name;
- replacement mesh `subMeshCount`;
- replacement material count;
- replacement rootBone name;
- replacement bone names;
- read-only predicted mapped/unmapped replacement bone names using the exact Dusk name-matching rule.

The postfix captures the same target renderer after Dusk completes and must prove whether the same renderer component now references a different mesh. It records post-replacement mesh identity, live `blendShapeCount`/names, material count, `subMeshCount`, rootBone and mapped bone identities.

For the Janitor/Princess hypothesis the decisive live fact is whether the tracked Janitor renderer becomes the Princess replacement mesh with live `blendShapeCount == 0`.

## Required hook 3 — material/submesh correlation

Exact DawnLib.Dusk 0.9.25 source provides:

`MaterialsReplacement.CopyOrResizeMaterials(Renderer target, Material[] sourceMaterials, int requiredCount)`

which owns the existing `TransferRenderer: Material count mismatch (got ..., need ...)` warning.

A prefix/postfix may observe this exact helper only when `target` belongs to an already-tracked Janitor/SpringMan instance or to a selected non-default Dusk replacement currently being correlated. Required fields:

- target renderer instance/path;
- source material count;
- `requiredCount`;
- current mesh name/subMeshCount;
- post-call material count;
- current selected replacement identity.

This hook is correlation-only. It must not replace Dusk's warning and must not infer that a material-count mismatch is itself the array emitter.

## Required hook 4 — Janitor's actual index-0 blendshape writes

The version-anchored CodeRebirth 1.6.9 source evidence establishes four direct `SetBlendShapeWeight(0, ...)` callsites:

1. `Janitor.SetBlendShapeWeightClientRpc(int weight)` — direct write in the receive execution path;
2. `Janitor.KillEnemy(bool destroy = false)` — direct reset write;
3. `Janitor.KeepPlayerAttachedDuringZoom()` — direct reset write in its reset branch;
4. `Janitor.SwitchToChaseState(PlayerControllerB player)` — direct write to 100.

Indirect callers such as `ResetChaseAndRevertToIdle()` and `UpdateBlendShapeAndSpeedForChase()` are already covered by the ClientRpc receive-side direct write and must not create duplicate write records.

### Smallest exact observation

A later implementation should use one narrowly validated Harmony transpiler per exact Janitor method above, injecting a pure diagnostic callback immediately before the single proven `SkinnedMeshRenderer.SetBlendShapeWeight(0, value)` call. The original call and stack operands must remain unchanged.

Each target must fail static/runtime arming unless the exact CodeRebirth 1.6.9 declared method/signature/body is present and exactly one expected index-0 callsite is found in the expected structural context. No wildcard method search, no base-class patch, and no global patch of Unity's `SkinnedMeshRenderer.SetBlendShapeWeight` is permitted.

Each write record must contain:

- callsite label;
- Janitor/network instance identity;
- renderer instance/path;
- requested index and weight;
- current mesh name/instance ID;
- current live `blendShapeCount` and names;
- current material count and mesh `subMeshCount`;
- current Dusk replacement state/key;
- current exact-array-signature count;
- timestamp envelope.

The callback must only read state. It must never clamp, suppress, catch-and-ignore, remap, or substitute the blendshape write.

## Required hook 5 — Janitor/SpringMan equal-scope renderer snapshots

SpringMan remains a contemporaneous alternative and may not be excluded simply because Janitor has the stronger static mechanism.

The Dusk selector-postfix is the shared instance-registration point. For exact Janitor and SpringMan instances it schedules bounded read-only snapshots of that enemy root only:

- immediately after Dusk selection completion;
- once on the next main-thread frame, allowing Dusk's delayed replacement coroutine to execute;
- once on the first subsequently observed exact-array-signature onset, queued to the next main-thread frame.

No global object scan is permitted. Each snapshot walks only `GetComponentsInChildren<SkinnedMeshRenderer>(true)` under the tracked enemy root and records, per renderer:

- renderer/path/instance ID;
- mesh name/instance ID;
- `blendShapeCount` and all names;
- material count;
- `subMeshCount`;
- rootBone;
- bone names.

Janitor additionally identifies the exact `Janitor` hierarchy-path renderer used by Princess. SpringMan receives the same mesh/blendshape/material/bone snapshot schema even if no Dusk definition exists, so the alternative is tested rather than silently excluded.

## Required hook 6 — stackless array-flood correlation without ownership assumption

Subscribe read-only to Unity's log-message callback and filter only the exact condition:

`Array index (0) is out of bounds (size=0)`

The callback must not emit a log line from inside the callback. It only atomically records:

- cumulative count;
- first and latest wall-clock timestamp;
- first and latest monotonic timestamp;
- supplied `LogType`;
- whether the supplied stack string is empty/non-empty.

Main-thread diagnostic code may emit bounded summary markers after the callback returns: flood-begin, periodic low-frequency count summaries, and final count. Every Dusk/renderer/Janitor-write record also carries the current count, making temporal ordering possible without duplicating the 45/s flood or presuming native ownership.

The raw Unity error lines remain primary evidence for individual error cadence. The diagnostic listener is a correlation anchor, not an emitter-attribution claim.

## Other-enemy scope

To avoid tunnel vision, any non-Janitor/SpringMan enemy for which the selected-definition hook observes a non-default Dusk replacement receives a lightweight record containing enemy/network identity, selected definition identity, action types/paths and replacement timestamp.

It does not receive full per-renderer snapshots unless a later separate design change justifies that expansion.

## Required versus nice-to-have data

### Required

- Dusk selected non-default key/name or explicit no-nondefault/no-definition state;
- enemy component/GameObject identity and NetworkObjectId when spawned;
- replacement action type and hierarchy path;
- target renderer identity/path;
- original/replacement/live mesh identities;
- live `blendShapeCount` and names;
- material count and mesh `subMeshCount`;
- rootBone plus replacement mapped/unmapped bone names;
- all four actual Janitor direct index-0 blendshape writes;
- exact array-signature cumulative count plus first/latest timestamps;
- equal-schema SpringMan snapshots.

### Nice to have only

- active Animator state/clip names;
- material/shader names rather than counts;
- individual bone Transform instance IDs;
- current weather/route price/context already available elsewhere in logs;
- GC/frame-time/profiler metrics;
- full snapshots for every enemy.

Nice-to-have data must not widen the first implementation surface.

## Fail-closed / no-gameplay-change contract

A later implementation is allowed to arm only if all required identities validate exactly:

- exact deployed CodeRebirth 1.6.9 DLL identity from the existing evidence chain;
- exact deployed DawnLib.Dusk 0.9.25 DLL identity from the existing evidence chain;
- exact Dusk selector, selected-definition Apply target, `SkinnedMeshReplacement.ReplaceSkinnedMeshRenderer`, and `MaterialsReplacement.CopyOrResizeMaterials` declared contracts;
- exact four Janitor method contracts and exact expected direct index-0 callsite count;
- exact Unity log callback registration path.

If any required target/member/body differs, the diagnostic must unpatch/refuse to arm and preserve normal behavior. There is no guessed fallback target.

The implementation must also obey:

- postfix/prefix observers never change arguments/return values/state;
- Janitor transpilers only insert a logger call and preserve the original write;
- no Dusk candidate list/RNG mutation or replay;
- no mesh/material/bone/blendshape write by diagnostic code;
- no AI behavior-state, Animator parameter, navigation, NetworkVariable/RPC, spawn, death/despawn or ownership mutation;
- no config/profile/package/controller mutation;
- no `PatchAll`;
- no global per-frame object scans;
- observer exceptions disable that observer and log `INCONCLUSIVE`; they never skip original gameplay code;
- no logging from inside the Unity log callback;
- bounded/sampled diagnostic output so the observer does not create a second log flood.

## Runtime interpretation matrix for a later separately authorized run

### Janitor/Princess hypothesis materially confirmed for the observed instance

All of the following must occur on the same Janitor/network instance:

1. Dusk records the Princess definition (`code_rebirth:princess` or its exact runtime-equivalent stable identity) as the selected non-default replacement;
2. the `SkinnedMeshReplacement` action targets hierarchy path `Janitor`;
3. pre-state matches the original Janitor renderer and post-state shows the Princess replacement mesh;
4. post-state live `blendShapeCount == 0`;
5. an exact Janitor index-0 write is observed on that same renderer;
6. the exact array flood starts only after that replacement/write chain.

That would confirm the concrete runtime trigger chain and strongly support the Janitor/Princess zero-blendshape hypothesis. It would still not, by itself, prove the exact native Unity function that emits the stackless message.

### Janitor/Princess zero-blendshape mechanism contradicted for the flooding instance

Any one of these is sufficient to contradict that specific mechanism in a reproduced flooding instance:

- the flooding Janitor instance did not select Princess/non-default Dusk replacement;
- the tracked Janitor renderer never received the Princess replacement mesh;
- the live post-replacement Janitor mesh has a valid index 0 (`blendShapeCount > 0`) and the expected name set remains compatible;
- the flood is already active before any Princess replacement and before any Janitor index-0 write on the tracked instance.

This does not automatically identify SpringMan or another owner; it only rejects the specific Janitor/Princess zero-blendshape chain for that run.

### SpringMan/other alternative strengthened

SpringMan or another alternative becomes materially stronger when the flood reproduces while the Janitor/Princess chain is absent/valid, especially if the alternative's own renderer state changes immediately before onset. No root-cause label is permitted without an exact emitting path.

### Still unresolved

Attribution remains unresolved if:

- the target enemies/replacement state needed for comparison does not occur;
- no flood reproduces;
- Princess is selected and a zero-blendshape/write chain is present but the flood timing does not isolate it from another simultaneous mutation;
- required observer hooks refuse/inconclusive;
- network/renderer identity cannot be correlated unambiguously.

A non-reproducing run is negative reproduction evidence only, not proof that the prior 6696-message flood was harmless or impossible.
