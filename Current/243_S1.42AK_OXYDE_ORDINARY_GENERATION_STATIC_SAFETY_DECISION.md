## 3. LLL and Dawn: metadata versus execution

Existing C3E3E/C3E3G evidence separates the stages:

1. Moon registration, Dawn list population and metadata matching can occur with false. The 22 direct LLL matches plus Dawn-native Black Mesa matching establish the 23 supported metadata pairings.
2. The vanilla early return precedes LLL's replaced `GenerateNewFloor` callsite. LLL's helper cannot run merely because metadata matches. Its loaded-ExtendedLevel/true branch calls dungeon selection; its fallback calls `GenerateNewFloor`.
3. If reached, Dawn updates weights at `GenerateNewFloor` entry and replaces its final direct generation call with deferred bundle loading. It waits for the owner network bundle path where required, then delegates back to LLL size handling or applies its own clamp and generates.
4. Dawn's `RuntimeDungeon.Start` hook disables automatic startup generation. Its `Generate` hook adjusts fire-exit counts and injects tile sets before delegating. These installed hooks are not an independent route around the vanilla early return.
5. LLL `PrepareDungeon`/fire-exit adaptation applies to non-External **selected dungeon flows**; the moon being External is not the same predicate. Dawn's shared generation hook is separate.

Hypothetical reachability is not successful execution: active generator presence, loaded flow, network completion, hook ordering, geometry and lifecycle compatibility still require proof. The unchanged S1.42AB normalizer only equalizes already-positive selection weights; it supplies none of those prerequisites.

## 4. CodeRebirth special-level assumptions

Version-matched sources were reread at the pinned commit; blob identities are in the manifest.

- `OxydeCrane.Update` sets `currentDungeonType=-1` every frame. Vanilla generation writes a selected index (or fallback 0). **Inference:** an ordinary generated flow would coexist with a persistent contrary dungeon-type value. Exact failure in a downstream consumer is not proven; the competing writes are enough to reject a one-flag safety claim.
- Crane `Awake` disables the drop button/ship lever, registers a new-round event and starts a coroutine waiting for `dungeonCompletedGenerating && mapPropsContainer != null`, then calls `SpawnOutsideHazards`. `Update` gates the lever on `alreadyDropped`; the networked drop routine moves ship/nav colliders and holds their final pose. Waiting on completion is not generation. **Risk:** enabling generation changes timing dependencies and may overlap a normal hazard path; duplicate hazards or deadlock are not observed facts.
- `EnemyAIPatch.EnemyAI_Start` calls original Start, then, outside ship phase on scene `Oxyde`, calls `SetEnemyOutside(true)` and selects the nearest outside AI node as `favoriteSpot`. It does not distinguish a hypothetical newly spawned indoor enemy. **Inference:** conventional indoor enemies could be reclassified/routed outside; exact live effect depends on the enemy and effective patch order.
- `ShipAnimator` waits for Oxyde/non-ship phase and landing, disables the ship animator until leaving, waits for doors and phase transition, and routes the server to Gordion after all-player death. It also has achievement and animation-event effects. This remains active by scene/state predicates even if the generation flag changes. No source-proven flag-only bypass exists.
- `ItemDropshipPatch` resets the dropship timer on Oxyde door opening. `RoundManagerPatch` uses `!planetHasTime` for deadline-day recharge and hooks outside-hazard spawning for a conditional military-plane path. These are additional special-level interactions, not entrance constructors.
- `planetHasTime=false` is independent of the generation flag. A generation-only toggle does not set it true. Exact whole-game clock/terminal/leave consequences are outside the available focused V81 captures; do not infer conventional day progression or silently include a time change.

The combined asset/source pattern supports treating Oxyde as an exterior/special-level architecture. It does not establish complete author intent or permanent impossibility of interiors.

## 5. Entrance and generator prerequisites

C3E3B parsed all 965 scene MonoBehaviours without errors, resolving 963 non-null script references and retaining two null-script records on `DungeonGenerator`. No directly identifiable serialized `EntranceTeleport` or pairing fields were found. This neither proves zero runtime entrances nor proves an active `RuntimeDungeon` exists because of the GameObject's name.

Exact V81 `SetExitIDs` only renumbers existing inside-side ID-1 teleports. `FindExitPoint` requires equal ID and opposite `isEntranceToBuilding`; it creates nothing, and duplicate partners are unsafe because later matches can replace earlier ones. CodeRebirth's entrance patch only tracks existing instances.

Dawn counts existing non-main entrances under `OutsideLevelNavMesh` and sets GlobalProp 1231 counts; LLL similarly adapts counts/IDs from existing scene entrances. Neither inspected mechanism supplies a missing exterior main entrance. **Conditional:** if the root exists but contains no alternate teleports, Dawn requests zero standard fire exits; if that root is missing, its inspected direct dereference is an additional risk. Neither condition is asserted as Oxyde runtime fact.

Consequently merely making ordinary generation reachable cannot establish valid main/fire-exit topology. Before a future conversion, prove an existing runtime construction path or design a separate, explicit exterior entrance/construction mechanism with placement, interaction/colliders, network lifecycle, unique IDs, inside partners and traversable navigation. Standard GlobalProp adaptation is not such a mechanism. No arbitrary interior choice solves this whole-row prerequisite.

## 6. Minimality and future proof obligations

A field assignment is technically small but behaviorally broad. Bypassing only the RPC guard would also leave false-gated postprocessing/numbering/waits inconsistent; enabling the field activates them without removing the crane writer, outside-enemy conversion, timeless semantics or missing topology/generator proof. Neither is an established safe minimal change.

If Oxyde is deliberately revisited later, source/static prerequisites include exact packaged component/generator validity, final owner spawn tables, complete relevant V81 postprocessing/clock callees, exact-binary binding for changed owner methods, and a coherent entrance plus dungeon-type/enemy/ship lifecycle design. This is an unfulfilled future contract, **not authorization to acquire runtime evidence or implement it now**.

Only a separately authorized future candidate could then prove host/client generation and landing completion, valid main/all-exit bidirectional traversal, geometry/NavMesh, correct indoor/outside classification, scrap/hazard behavior, crane/drop/leave/death routing, time behavior, repeat visits, cleanup and unaffected non-Oxyde control behavior.
