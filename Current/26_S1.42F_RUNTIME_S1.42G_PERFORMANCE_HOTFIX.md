## Coroner spam — confirmed separate performance defect

The same log contains:

`16,138` occurrences of:
`Could not access dying player`

Including:
- 8,066 x `PlayerController was null`
- 8,069 x `Index not assigned!`

Typical sustained rate:
roughly 300-400 Coroner warning lines per second.

The exact source is Coroner's:
`Coroner.Patch.JetpackItemUpdatePatch`

which Harmony-patches:
`JetpackItem.Update()`

Every frame it runs:
`__state.TrySetPlayer(__instance.playerHeldBy)`
then:
`__state.QueryPlayerState()`

When a Jetpack exists but is not held:
`playerHeldBy == null`

This produces:
1. `PlayerController was null`
2. `Index not assigned!`

every frame.

Direct runtime evidence:
- an unheld `JetpackItem(Clone)` is restored/initialized in the ship;
- the alternating Coroner warnings then repeat continuously at frame-rate cadence.

Historical cross-check:
S1.42C showed the same correlation:
- an unheld Jetpack initialized in the ship;
- the Coroner `PlayerController was null` flood begins at the same moment.

This Coroner defect predates S1.42F, but it is severe log/per-frame overhead and must be removed before further regression testing.
