## Decision

The bounded repository-native root-cause analysis of the exact `S1.42AK-BMGHDIAG2` startup refusal is complete.

The immediate runtime failure is proven: `RuntimeIdentityPolicy.ValidateAssemblyIdentity(...)` checks, in order, exact type full name `EntranceTeleport`, declaring assembly simple name `Assembly-CSharp`, non-dynamic assembly state, and finally exact manifest module name `Assembly-CSharp.dll`. The ingested runtime stack reaches the distinct fourth failure text `EntranceTeleport manifest module identity mismatch.` Therefore the loaded runtime target had already passed the first three predicates and had a non-null `ManifestModule`, but `runtimeAssembly.ManifestModule.Name` was not exactly `Assembly-CSharp.dll`.

`Plugin.Awake()` validates the exact physical installed game assembly hash, resolves the exact LLL selection contract, and only then calls `ResolveObservationContract()`. The runtime refusal therefore does not invalidate the physical V81 source hash or the earlier exact selection/dependency gates.

## Root cause

BMGHDIAG2 correctly separated physical installed-binary provenance from loaded runtime structural identity after BMGHDIAG1. However, it then carried the physical source filename `Assembly-CSharp.dll` into the loaded Reflection contract as an exact `ManifestModule.Name` invariant without runtime evidence that the live preloader-transformed module preserves that filename.

The exact runtime evidence disproves that assumption in the real profile stack:

- BepInEx `5.4.23.5` starts with 15 patcher plugins before normal plugin loading.
- The preloader explicitly patches `Assembly-CSharp` through multiple components.
- `InjectionLibrary.Preloader` logs `Patching Assembly-CSharp.dll` and directly injects `CodeRebirth.src.Util.PreloaderInjections.IOnDestroyMethod` into `EntranceTeleport`, adding an `OnDestroy` method before BMGHDIAG2 resolves the runtime type.
- The exact profile has `DumpAssemblies = false` and `LoadDumpedAssemblies = false`; the documented BepInEx setting therefore keeps the normal patched-assembly memory-loading path instead of loading persisted dumped assemblies.

The supported design root cause is consequently: **BMGHDIAG2 treated the physical installed source filename as a stable fail-closed identity predicate for a preloader-modified, memory-loaded runtime Reflection module. That equality was unproven and is false in the actual stack.**

This finding does not attribute the resulting module name to one specific preloader, Mono, Mono.Cecil/MonoMod, or BepInEx internals. The exact actual `ManifestModule.Name` and `ScopeName` remain unmeasured, and no component-level ownership claim is made.
