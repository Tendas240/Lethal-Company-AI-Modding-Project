## Reconstructed selection path

Repository-captured installed-V81 evidence at `SourceEvidence/VanillaV81/RoundManagerGeneration/20260920T095502Z-fa6b63a6/ROUNDMANAGER_GENERATION_FOCUSED_DECOMPILE.txt` establishes the following exact boundaries from `Assembly-CSharp.dll` SHA-256 `5f7db5538b78dc408845a3002907619785ac9f9c6b6059d13dc9a602d9b65731`:

1. `LoadNewLevelWait(int randomSeed)` forwards the same `randomSeed` into `GenerateNewLevelClientRpc(...)`.
2. `GenerateNewLevelClientRpc(...)` assigns `playersManager.randomMapSeed = randomSeed`, then calls `InitializeRandomNumberGenerators()` before dungeon generation.
3. `GenerateNewFloor()` constructs a rarity list in `currentLevel.dungeonFlowTypes` order and calls `GetRandomWeightedIndex(list.ToArray(), LevelRandom)`.
4. Only after the dungeon-flow index has been selected does `GenerateNewFloor()` consume `LevelRandom.Next()` for the DunGen generator seed.

The source-locked LethalLevelLoader 1.7.12 path establishes that LLL computes the valid `ExtendedDungeonFlowWithRarity` pool, serializes the viable names/rarities in list order, temporarily installs the resulting `IntWithRarity[]` into `SelectableLevel.dungeonFlowTypes`, calls the native `RoundManager.GenerateNewFloor()` path, and restores the cached array afterward. LLL therefore supplies the viable weighted candidate list but does not perform the final random draw itself.

The complete bodies of `InitializeRandomNumberGenerators()` and `GetRandomWeightedIndex(...)` are not yet stored as a new exact-hash installed-V81 focused capture in this repository. A version-aligned public V81 `RoundManager.cs` snapshot at `snowlance7/Rats`, commit `c80c57b9af7e4b9afa660ecacbc71d76e84e454e`, supplies the missing body-level bridge: `LevelRandom = new System.Random(playersManager.randomMapSeed)`, and the weighted helper uses one `NextDouble()` draw when the positive total weight is non-zero, accumulating normalized weights until the draw is reached. This external body-level bridge is therefore retained with an explicit provenance qualification rather than promoted to exact installed-binary proof.

For the current Black Mesa pool, every positive viable rarity is normalized by the accepted S1.42AB patch to exactly `100`. The final weighted draw therefore reduces to one equal-probability interval per viable flow, while still using the actual seeded `System.Random` path rather than any `seed % 31` shortcut.
