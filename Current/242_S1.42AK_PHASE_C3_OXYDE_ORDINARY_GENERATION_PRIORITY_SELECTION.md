## Decision

The next Phase C3 compatibility/safety target is the **Oxyde ordinary-generation semantic restriction**, not another arbitrary Black Mesa pair.

The next bounded checkpoint must remain source/static and repository-native. It must determine whether Oxyde's exact current `spawnEnemiesAndScrap=false` / ordinary-generation early-return behavior is an intentional or otherwise necessary owner-level constraint, what exact game/LLL/Dawn/CodeRebirth behavior would become active if that semantic were changed, and whether any minimally scoped safe change is technically plausible.

This checkpoint does **not** authorize changing that flag, modifying Oxyde, building a candidate, or running gameplay.

## Why Oxyde is the next priority

Black Mesa and Oxyde are not at the same remaining proof boundary.

### Black Mesa

Current owner applicability is already closed at:

- 31 `MATCH`;
- 22 `NON-MATCH`;
- 0 `UNRESOLVED`.

Black Mesa also now has multiple concrete Phase-C pair lines:

- Greenhouse — full bounded runtime-compatibility PASS;
- Slaughterhouse — topology/materialization PASS evidence;
- Expanded facility — topology/materialization PASS evidence;
- Decrepit store / StoreFlow — topology/materialization plus partial traversal evidence;
- Substation — topology/materialization plus direct traversal evidence;
- Abandoned Foundry — full bounded runtime-compatibility PASS.

No additional already-ingested Black Mesa concrete pair remains available for the same evidence-only reconciliation path. Choosing another Black Mesa `MATCH` now would therefore require selecting a new evidence-acquisition target. That may become appropriate later, but current evidence does not justify preferring one unseen Black Mesa pair over the structural Oxyde blocker.

The regular Black Mesa x `DeepSewersFlow` BMDSFIX1 target remains separate, passive, outstanding and unwaived. It is not selected here and no dedicated reroll is released.

### Oxyde

Oxyde currently has **23 selection-supported metadata pairings**, but exact repository evidence establishes a whole-row execution boundary:

1. packaged Oxyde has `spawnEnemiesAndScrap=false`;
2. exact V81 returns before the ordinary `RuntimeDungeon` / `GenerateNewFloor` path when that flag is false;
3. the exact Oxyde scene bundle exposes no directly identified serialized `EntranceTeleport` topology;
4. inspected CodeRebirth/Dawn owner paths do not establish an independent dungeon/entrance-construction route;
5. Oxyde-specific behavior includes exterior/special-level handling such as `currentDungeonType=-1`, Oxyde-specific ship behavior and outside-hazard logic.

Therefore an individual Oxyde x Interior compatibility test is premature: ordinary interior generation itself is not currently established as executable. The whole-row semantic restriction must be understood first.

## Priority rationale

This selection follows the universal-availability objective and the Phase-C safety contract:

- Oxyde's restriction affects the entire External moon row, not one pair;
- resolving its semantics has higher prerequisite value than acquiring another isolated Black Mesa pair;
- current Black Mesa evidence already proves that its external-moon topology can support multiple distinct interiors;
- current Oxyde evidence proves that positive selection metadata alone cannot reach ordinary generation;
- changing Oxyde's semantics without understanding owner interactions could alter enemies, scrap, hazards, ship lifecycle, moon classification and dungeon state, so implementation before source/static impact analysis would be unsafe.

This is a priority-selection result only, not a conclusion that the Oxyde restriction should be removed.

## Required next analysis

The next bounded Oxyde source/static analysis must answer, from existing repository/package/source evidence only:

1. **Ownership:** which exact package/asset/source authority sets or preserves `spawnEnemiesAndScrap=false`, and whether any current config surface can override it without patching runtime state.
2. **Vanilla consequence:** the exact V81 code paths skipped by false and reached by true, especially dungeon selection/generation, enemies, scrap and map-object lifecycle.
3. **LLL/Dawn consequence:** which current LLL/Dawn integrations would begin participating if ordinary generation became reachable.
4. **CodeRebirth consequence:** interactions with Oxyde-specific behaviors already proven in current evidence, including outside-enemy handling, ship/landing behavior, `OxydeCrane`, `currentDungeonType=-1`, time semantics and any lifecycle observers that assume the special-level path.
5. **Entrance/topology prerequisite:** whether enabling ordinary generation alone could construct a valid entrance topology, or whether an additional entrance/construction mechanism would still be required.
6. **Minimality/safety:** whether a narrowly scoped semantic change is technically plausible at all, or whether the Oxyde exception should remain explicit in the universal-availability target.

The analysis must distinguish:
- source/static plausibility;
- owner intent where actually evidenced;
- inferred risk;
- facts that would still require runtime proof.
