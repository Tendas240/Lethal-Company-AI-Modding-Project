## Decision

A deterministic selector for **Tower / `TowerFlow` on Offense** is technically designable by reusing the repository-proven **selector-only one-postfix architecture** already validated end-to-end by AGDIAG1, DRDIAG1, LFDIAG1 and SHDIAG1.

The reusable architecture is:

> Apply exactly one postfix to `LethalLevelLoader.DungeonManager.GetValidExtendedDungeonFlows(ExtendedLevel, bool)`, ordered after the accepted S1.42AB normalizer at `Priority.Last`; on the validated real Offense server-selection path, verify that exactly one already-returned Tower wrapper exists with `DungeonName == "Tower"`, exact `DungeonFlow.name == "TowerFlow"`, and final normalized rarity `100`; only then reduce that fresh returned list to the same existing wrapper as a singleton.

This remains a **selection-only diagnostic technique**. It must not manufacture eligibility, rewrite rarity, register a dungeon, change generation parameters, patch traversal, alter entrance topology, mutate NavMesh, hook RNG, replace the selection RPC, or change enemy/scrap/BCMER behavior.

The existing AGDIAG1, DRDIAG1, LFDIAG1 or SHDIAG1 binaries, identities and source trees must **not** be retargeted or repurposed. Any later Tower implementation requires a new separately versioned diagnostic identity and source tree.

This preflight authorizes **no source implementation, compile, build, publication, Gale import, activation or runtime execution**.

## Why selector reuse is supported

Tower satisfies the same prerequisite shape as the completed direct-LLL diagnostic cycles:

- exact Offense classification: `VIABLE_EQUAL_100`;
- availability mechanism: `DIRECT_LLL_UNIVERSAL_TAG_OVERRIDE`;
- canonical LLL dungeon name: `Tower`;
- exact flow asset: `TowerFlow`;
- final normalized rarity expected to be exactly `100`;
- no owner-hard-block bypass is required;
- record 245 preserves no Tower-specific generation, CullFactory, route/NavMesh, topology or owner-safety warning.

The exact accepted S1.42AK LLL config additionally confirms the active Tower section itself:

- `Enable Content Configuration = true`;
- `General Settings - Enable Dynamic Dungeon Size Restriction = false`;
- `Dungeon Injection Settings - Manual Level Names List = Default Values Were Empty`;
- `Dungeon Injection Settings - Dynamic Level Tags List = Vanilla:100,Custom:100`.

This config evidence establishes Tower availability through the project-controlled direct LLL tag rule; it is not generation proof.

The architecture is now validated four times end-to-end:

1. AGDIAG1 proved that one post-normalizer selection postfix can retain the exact already-viable rarity-100 wrapper while ordinary downstream generation/materialization logging remains intact.
2. DRDIAG1 reused the same architecture for another `DIRECT_LLL_UNIVERSAL_TAG_OVERRIDE` target and completed the generation/materialization proof without a second observer patch.
3. LFDIAG1 repeated that result for `BackroomsFlow`, with normal downstream generation completion, exact CullFactory materialization and concrete PathfindingLib entrance relationships.
4. SHDIAG1 repeated the same result for `SHFlow`, proving completed floor generation, exact CullFactory `SHFlow` materialization and a complete concrete four-direction PathfindingLib relationship set.
5. All four diagnostics remained `DIAGNOSTIC ONLY / NEVER ACCEPT`; none established natural target-selection frequency.

Therefore no new source investigation is required to justify the interception **surface** for Tower. Any later implementation still requires its own exact target literals, new identity, pure fail-closed tests, static validator, Patch Safety Review and dedicated source/static workflow.

Mandatory:

### B. Completed generation and exact-flow materialization

Mandatory:

- `Dungeon has finished generating on this client after multiple frames`;

### C. Entrance/materialization proof

Mandatory:

- PathfindingLib records the complete and unambiguous concrete exterior/interior `EntranceTeleport` relationship set for the generated Tower layout.

The established basic model commonly produces four logical directional relationships for an ordinary main/alternate pair structure, but this preflight does **not** assume Tower must have exactly that topology. If the actual generated Tower topology differs, reconciliation must classify the concrete complete relationship set rather than forcing an artificial four-line requirement.

Direct player traversal remains optional for the basic generation/materialization tier.

### D. Negative/isolation boundaries

Mandatory:

- no persistent target-correlated generation failure preventing completion;
- no invalidating diagnostic refusal after arming;
- no unexpected `[BMDSFIX1] APPLIED` marker on Offense.

Isolated RuntimeNavMeshBuilder or route/reachability warnings do not erase positive generation proof by themselves unless tied to a concrete blocking failure. Such signals remain separate route/NavMesh evidence.
