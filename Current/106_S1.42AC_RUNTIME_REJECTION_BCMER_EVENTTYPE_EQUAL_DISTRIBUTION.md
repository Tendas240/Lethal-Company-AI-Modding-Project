## Primary acceptance gate — FAIL

S1.42AC attempted to make all eight BCMER EventTypes equally likely by setting the eight `[_EventType Weights]` scales in `Difficulty_Settings.cfg` to the identical constant curve:

`12.5, 0.0, 12.5, 12.5`

`Use custom weights? = false` remained preserved.

The runtime gate required all eight BCMER lines for the same roll context:

`Set eventType weight for <type> to <value>`

and required the resulting values to be identical.

The fresh runtime log contains five repeated roll contexts. In every observed context the effective values were:

| EventType | Runtime weight |
| --- | ---: |
| Insane | 6843 |
| VeryBad | 506 |
| Bad | 355 |
| Neutral | 1368 |
| Good | 1244 |
| VeryGood | 2737 |
| Rare | 27375 |
| Remove | 883 |

These values are strongly unequal. Therefore the target fixed normalized distribution of `8 × 12.5%` was **not achieved**.

This is acceptance-blocking and is sufficient to reject S1.42AC.

## What the runtime evidence proves about the config assumption

The accepted S1.42AB runtime already emitted unequal final BCMER EventType weights, but with a different set of values. S1.42AC changed those final values, so the eight configured EventType scales do influence the BCMER calculation.

However, setting all eight scales to the same constant does **not** make the final EventType weights equal. BCMER 1.71.0 therefore applies additional type-dependent calculation/weighting after or together with those scales.

Do not treat the exact internal formula as proven until the actual BCMER 1.71.0 calculation path is inspected. The evidence proves the previous semantic assumption was wrong; it does not by itself prove the complete formula.

### Do-not-repeat rule

Do **not** build another successor that merely sets all eight EventType scale curves to the same value and assumes this implies equal final selection probability.

The next implementation must first identify the exact BCMER 1.71.0 code path that produces the final `Set eventType weight for ...` values.
