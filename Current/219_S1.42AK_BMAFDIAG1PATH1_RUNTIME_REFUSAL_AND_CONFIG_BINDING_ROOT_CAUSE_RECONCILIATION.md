## Root cause — exact LLL category identity

Pinned LethalLevelLoader 1.7.12 source commit:

`f9998b91adf242cd8d735f4e697d55b32b94bfac`

LLL constructs Custom Dungeon config categories through `ConfigTemplate` with sorting priority 9. `GetSortingSpaces()` prepends exactly nine U+200B ZERO WIDTH SPACE characters before the visible category name. Therefore the actual category identity for Foundry is:

`[​​​​​​​​​Custom Dungeon:  Abandoned Foundry]`

The repository-held owner-generated runtime config at:

`RuntimeEvidence/S1.42A/20260902T224318Z/extracted/config/config/LethalLevelLoader.cfg`

contains exactly that nine-U+200B header.

The published BMAFDIAG1/PATH1 config instead contains:

`[Custom Dungeon:  Abandoned Foundry]`

with zero U+200B characters.

BepInEx/LLL category binding is therefore pointed at a different category from the one materialized by the build. The intended `Enable Content Configuration = true` and `Black Mesa:100` values existed textually but were not bound to the real LLL Foundry config entries.

## Builder and validator defect

`BuildSystem/profile_builder.py::set_ini` constructs the requested section as plain:

`header = f"[{section}]"`

and performs a raw case-folded string comparison. Since exact accepted S1.42AK had no matching plain Foundry section, the builder appended the plain category at file tail.

The BMAFDIAG1 build validator then used `visible()` to remove every Unicode character whose category is `Cf` before evaluating Foundry section identity. U+200B is `Cf`, so the validator incorrectly treated the real nine-U+200B LLL category and the plain category as equivalent. This masked the exact semantic difference that controls config binding.

The inactive review-build PASS therefore remains valid only for the checks it actually performed; its claim that the materialized Foundry section was a runtime-bindable LLL category is superseded by this runtime/root-cause evidence.
