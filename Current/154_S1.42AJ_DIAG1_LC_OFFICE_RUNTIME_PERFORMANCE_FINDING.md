## Performance triage

The first hypothesis was that LC Office RuntimeNavMeshBuilder read-access errors directly caused the later stutter. That hypothesis is now downgraded rather than treated as proven:

- DIAG1 contains a large burst of LC-Office mesh-readability errors during dungeon generation.
- The accepted S1.42AI baseline nevertheless contained substantially larger repeated `Failed to create agent because it is not close enough to the NavMesh` warning volume and also contained RuntimeNavMeshBuilder read-access errors.
- The DIAG1 mesh-readability errors are concentrated around generation rather than continuously matching the later user-reported stutter period.

Therefore those NavMesh signatures remain relevant compatibility evidence but are not sufficient evidence for a project-local NavMesh patch.

## Narrow A/B hypothesis

Upstream LC Office code in `Piggy3590/LC_Office`, `Components/CameraCulling.cs`, periodically invokes `Camera.Render()` when Office cameras are enabled and the local player is within render distance. LC Office exposes the existing config key `[General] Camera Frame Speed`; its code treats value `0` as disabled and then skips the periodic camera-render path.

The active profile uses LC Office's default camera frame speed rather than a project override. This gives a narrower and safer performance hypothesis than introducing a Harmony/NavMesh patch.

This is a **working hypothesis only**. No causal claim is accepted until an isolated A/B run confirms it.
