## Why S1.42AA is rejected

S1.42AA changed only `Inject Dynamic Matching Weights = true -> false` in `LethalLevelLoader.cfg`. Fresh runtime evidence on Offense proved that this did not equalize the effective pool. LethalLevelLoader still reported unequal viable weights including LiminalHouse 300, Sub Systems 275, Abandoned Foundry 250, Shatteredrooms 75, Lead Factory 70, Spelunkers Caverns (Random) 50, Crimson Keep 35 and multiple 25/20 entries.

The underlying LLL matching implementation raises a flow's rarity to the highest matching source. A generic `Vanilla:100,Custom:100` match therefore cannot lower a stronger author/planet/mod match such as 300 to 100.

S1.42AA must not be promoted and its `Inject Dynamic Matching Weights = false` experiment must not be inherited.

## Goal

Equalize the effective selection probability of all dungeon flows that LethalLevelLoader has already determined are viable for the current level, while preserving every upstream exclusion and eligibility decision.

Target rule:

- flow excluded by LLL -> remains excluded;
- flow returned by LLL with positive rarity -> rarity becomes exactly 100;
- no new flow is registered or appended;
- no returned flow is removed or deduplicated;
- no Enemy/Scrap/MapObject rarity path is changed.

This architecture also implements the permanent project rule for future interiors: a newly added interior automatically receives effective rarity 100 whenever LLL considers it viable, without requiring a new per-interior weight entry.

## Runtime intervention

Patch target:

`LethalLevelLoader.DungeonManager.GetValidExtendedDungeonFlows(ExtendedLevel, bool)`

Intervention:

- Harmony Postfix only;
- original method always runs;
- after LLL returns its already-filtered `List<ExtendedDungeonFlowWithRarity>`, set each positive returned `rarity` to 100;
- do not alter list membership or list order.

Because LLL emits its built-in `Viable ExtendedDungeonFlows` debug line before returning, that original line can still show pre-normalization author weights. S1.42AB emits an explicit post-normalization runtime line:

`[InteriorWeightNormalization] Final effective viable pool for <level>: ...`

This project-local marker is the authoritative acceptance evidence for the effective pool used after the Postfix.
