# Jetpack implementation resolution

## Requirement

Increase the base Jetpack acceleration modestly as an always-on behavior.

This is not a purchase-gated ship-upgrade buff and must not be implemented by changing More Ship Upgrades `Jet Fuel` configuration.

## Exact runtime owner

Installed/frozen ButteRyBalance version:

`0.7.0`

Owner GUID:

`butterystancakes.lethalcompany.butterybalance`

Relevant owner code:

`ButteRyBalance.Patches.Items.JetpackPatches.JetpackItem_Pre_Update(JetpackItem)`

Exact target method:

`JetpackItem.Update()`

Relevant field:

`JetpackItem.jetpackAcceleration`

Under the accepted S1.42U configuration:

- `Control Scheme = V49`;
- `Warmup Period = false`.

ButteRyBalance v0.7.0 writes `jetpackAcceleration = 10f` for the local player in its `JetpackItem.Update` prefix on every frame. Therefore there is no effective narrow numeric config-only base-acceleration knob to change while keeping the accepted V49 behavior intact.

Do not switch V49 to Vanilla or Dynamic merely to approximate the requested buff.

## Frozen target

Base acceleration:

`10f -> 12f`

This is a +20% increase. It is intentionally modest and only changes acceleration, not the separate maximum-speed/power layer.

## JetpackFixes interaction

Installed/frozen JetpackFixes version:

`1.6.3`

Owner GUID:

`butterystancakes.lethalcompany.jetpackfixes`

JetpackFixes patches the same `JetpackItem.Update()` with a transpiler and postfix for collision/death/control fixes, but does not write `jetpackAcceleration`.

Preserve:

`MidAirExplosions = Off`

JetpackFixes keeps high-speed ground/collision death semantics around the 50u/s threshold. The acceleration increase can make high velocity arrive sooner, so this exact adjacent behavior is part of the S1.42V runtime gate. The patch does not raise that threshold or alter JetpackFixes safety logic.

## More Ship Upgrades interaction

Installed/frozen More Ship Upgrades version:

`3.14.1`

Owner GUID:

`com.malco.lethalcompany.moreshipupgrades`

`Jet Fuel` is purchase-gated and remains configured at:

- `Initial Acceleration Increase = 20`;
- `Incremental Acceleration Increase = 20`.

More Ship Upgrades inserts its percentage calculation where the original `JetpackItem.Update()` reads `jetpackAcceleration`. Therefore a purchased Jet Fuel upgrade remains a distinct percentage layer on top of the new base value. Example at the first +20% level: `12f -> 14.4f` at the read site.

`Jetpack Thrusters` is a separate maximum-speed/power owner and is untouched.

## Exact interception

- concrete type: `JetpackItem`;
- exact method: declared parameterless `void Update()`;
- patch type: Harmony Prefix;
- ordering: `[HarmonyAfter("butterystancakes.lethalcompany.butterybalance")]` plus `Priority.Last`;
- local-player gate mirrors ButteRyBalance;
- mutation is performed only when `jetpackAcceleration` is still approximately `10f`;
- exact replacement is `12f`;
- every non-10 value is left untouched.

## Why this interception is the smallest safe option

The original `JetpackItem.Update()` owns broad movement, physics, collision/death and state-transition responsibilities. Replacing/skipping the original method would be unsafe. Adding another IL transpiler would also increase collision risk because JetpackFixes and More Ship Upgrades already transpile the same method.

A late prefix changes only the proven ButteRyBalance-owned input field immediately before the original method consumes it. No original lifecycle is suppressed and no existing owner is replaced.

A postfix is intentionally not used because it would run after the original frame already consumed the 10f value and ButteRyBalance would write 10f again before the next original Update.

## Fail-closed validation

The patch refuses to arm unless all frozen assumptions hold:

- ButteRyBalance exactly `0.7.0` is loaded;
- JetpackFixes exactly `1.6.3` is loaded;
- More Ship Upgrades, when loaded, is exactly `3.14.1`;
- exact declared `void JetpackItem.Update()` exists;
- ButteRyBalance owns a prefix on that exact target;
- JetpackFixes owns a transpiler on that exact target;
- More Ship Upgrades owns a transpiler on that exact target when loaded;
- post-patch verification confirms the project-local prefix was applied.

There is deliberately no fallback method scan, broad signature match, alternate field owner, original-method skip, reverse-patch, or IL rewrite.

## Inheritance/lifecycle review

The patch targets the concrete `JetpackItem.Update()` implementation only. It does not patch a base `GrabbableObject`/network lifecycle method and does not suppress inherited behavior.

The only project-local state change is the existing instance float field `jetpackAcceleration`. No new RPC, NetworkVariable, persistent save state or host-authoritative ownership is introduced.

Network/client behavior mirrors the existing ButteRyBalance local-player gate: each client running the same profile adjusts its own locally controlled Jetpack path.
